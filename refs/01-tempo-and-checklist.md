# 01 · 节奏与检查单（时间盒 / 换线 / 落盘 / 停止条件 / 赛前赛后固定动作）

> **何时读**：开赛前 15 分钟、每解完一题、以及**任何一次"我是不是在空转"的自我怀疑出现时**——尤其当你准备第 3 次重复同一方向、准备再开一个会话、准备"先把这条线跑完再说"的时候。
> 来源：`ctf-challenge-playbook` §一 赛制决定的战术 / §2.3 时间盒 / §3.2 人机分工 / §3.3 上下文纪律 / §3.4 资源预算治理 / §八 一页赛前检查单；`westlake-ctf-agent` §四 标准解题循环 / §四·五 动态抢分决策规则 / §七·六 提速纪律 + 有效提示词模式；`zeekr-ctf-2026` §五 提速纪律（2.5 小时版）/ §7.12 跨会话资源治理；`xiaoyuan-ctf-2026` §四 解题纪律。

**结论先行**：慢不是因为题难，是因为四条——①旧结论不重验 ②线索不当提示词 ③单线串行且结果不落盘 ④无预算地开会话。这四条的根因都是**同一个东西**：没有机械闸门。下面每一条都是闸门，不是建议。

## 一、赛制决定战术（先搞清"分是怎么没的"，再决定先做哪题）

| 赛制特征 | 战术含义 |
|---|---|
| 动态积分（初始分每人解出 -1%，最低衰减到 80%／本轮实测最低 50、另一赛最低 200） | **早交高分**。开局 30–60 分钟把"稳解的简单题"刷完交掉；犹豫=丢分 |
| 同分比用时 / 同分按**最后一道题提交时间**排 | 每一分钟都值钱；**确定就交，别压着** |
| 前三名额外奖励原始分 30/20/10 | **抢首杀**：能快速确定的题优先，收益高于多解一题 |
| 分两批上题（如 13:00 / 14:00；短赛 10:45 左右） | **到点必须回头重扫题目列表**，漏看新增题=白丢分 |
| 赛后 N 小时内交 WriteUp（常见 2 小时） | **解一题立刻写一题**，绝不攒到最后（多数赛事 WP 一票否决） |
| 全程录屏 + 裁判电话抽查 | 每题自己至少能讲出主线；解法必须有**可复现的落盘证据** |
| 题型以某一大类为主体（如固件分析） | 该类的**解包链/脚本要在赛前热好跑通**，赛中不做环境搭建 |
| 平台明文允许 AI 解题 | 放开用 web_search 查知识点、用 AI 跑批量脚本——但**"允许 AI" ≠ "允许扫描平台"** |

**每次取题前先查 `solveCount`（解的人数）**：
- **solve > 4 的先做**——大家都在解，说明相对简单/有热度，且分数正在快速下降，**先抢动态分**；
- solve 少的题分数还高但难/没人碰，**留到后面**；
- solve 数来源：Agent API `exercise-list` 是否带 `solvedCount`；没有就看网页控制台"解题进度"表（浏览器观察）或 dashboard/ranking（需新 JWT）。
- 开局（0~约 1 小时）例外：优先做**本队擅长的常规题**（Web 反序列化/上传、Pwn 堆、Crypto 数论、Misc 编码）——已验证过的能力，稳拿分。

## 二、按赛制长度分档的节奏（各场真实差异，别把 2.5 小时的打法搬到 21 小时）

四场赛事实测过三种长度，**节奏不是同一套**：

| 档位 | 实测赛制 | 分诊时限 | 目标节奏 | 特别动作 |
|---|---|---|---|---|
| **短赛 ≤3 h** | 2.5 h（09:30–12:00，动态分最低 200，前三名加 30/20/10） | 开局 **10 分钟**必做完分诊 | 先刷快题，抢首杀 > 多解一题 | **10:45 左右回扫题目列表**防漏新题；`12:00` 前 20 分钟进入停止条件 |
| **中赛 3–4 h** | 4 h（13:00 开赛，分两批上题 13:00 / 14:00） | 开局 10 分钟清点 + 分快题/硬题 | 开局 30–60 分钟把稳解的简单题全刷完交掉 | **14:00 必须回扫题目列表**；赛后 2 h WP 窗口 |
| **长赛 ≥8 h（含过夜）** | 21 h 不间断（12:00 ~ 次日 09:00，题分动态变化） | 开局 30 分钟 | 前段广撒快题、中段啃硬题、尾段留足交付时间 | **必须轮换/睡觉**，靠落盘交接而不是靠会话不关；次日 09:00 后是提交题解窗口，**不是解题窗口** |

**理论赛/客观题（如 09:00–11:30 选择题，倒计时）**：逐题作答，**交卷不可取消**，交前核对全部答案与标记；不会的题直接 `web_search` 查资料（互联网可用时）。**理论赛与解题赛各开一个独立会话**，别混在一条上下文里。

## 三、标准解题循环（一条流水线，每个箭头都要落盘）

```
取题(--list) → 建 <题目录>/（一题一目录）→ 登记 challenges.json
→ --detail 拿附件+靶机 → 需要初始化则 build-env 并轮询到 running
→ 附件下载（url 直下；压缩包密码常在题目信息内）
→ 侦察 → 新鲜分析 → 需要时才查"手法索引"验证 → 本地验证 → 提交 → 记录
→ 卡题 → consult 集群 / 派子 agent 并行（先到先用）
→ 解出 flag → 提交
→ **提交正确才停另一条线**；提交错误（假 flag）不停：主线 + 先出结论的那条继续分析，
   晚出的那条降级为候选思路 → 直到正确
→ 立即写 WP（谁方便谁写）到该题目录 → 登记索引
→ 每题立即更新 challenges.json + notes/
```

**每一步的落盘要求**（这是"单线串行+结果不落盘"那条根因的解药）：

- 子 agent / 后台 job 的产物**必须是文件**（含分批进度文件，如 `flagN.txt` 逐字符进度）；消息回传只作摘要。后台 job 丢失即归零重做，血亏。
- 长任务（外带/爆破/扫描/开靶机）全部后台 job + **逐进度文件日志，断点可续**。
- **交接文档写清"停"的条件**，否则接手者会继承一个错误方向继续规模化。

## 四、时间盒（真执行，不是写着好看）

### 4.1 单方向 15 分钟到点

到点三选一，**不许"再来一轮"**：

1. **换线**（换假设、换数据源、换入口）；
2. **问用户**（要提示原文/要人操作）——立刻给一条可复制命令，别让用户干等；
3. **在同一轮里派子 agent 并行**（fresh spawn）。

**卡题禁止同一方向第三轮重复。** 反例都是真事：连写 ~20 个同族 `patch*.py` + 58 个 `gp_out_fd*.bin`；慢会话连写 9 个 fuzz + 5 个 exfil 脚本。

> **时间长 ≠ 有进展。产出物应该是"缩小假设空间的事实"，不是"又多一个脚本"。**

### 4.2 同一个动作重复第 3 次就是错

第 3 次之前必须换一个**能区分两种假设**的实验，而不是换一个参数再试一遍。

### 4.3 同一道题不要开多个目录

真事故：同一道题（多任务题）在 37 秒内起了 3 个目录、187 个文件，三份都从 `id; hostname; uname -a` 重来。
→ 多任务题（任务一/二/三）应该**一个目录 + 一份作战图**，任务只是目录里的章节。

## 五、停止条件（触发就停下来报告，不要继续硬啃）

以下任一条命中 → **立即停止当前方向并报告**，不是"再试一次"：

1. 同一方向第 3 次不成功；
2. 需要用户操作（GUI/账号/人决策）；
3. 要提交一个**不确定**的 flag；
4. 距比赛结束不足 **20 分钟**（含 WP 提交窗口）；
5. 响应延迟 >20 s/轮、连续 `TRANSPORT`/额度类失败、子会话被运行时自动 `stop` —— 见 §七；
6. 两次结果不一致 / oracle 自相矛盾（>96 真且 >1 假）→ 停手查**工具/链路本身**。

**交接提示词里必须写死这一条**：模板写"全程自动化：不要中途停下来问我确认"是错的——真事故里 Agent 在错误方向上持续规模化，逼得用户亲自打断（原话："你给我指令我自己运行"、"？你能不能先给我运行 ORW 的指令再去继续？？？"）。
正确写法：**"默认不停；但同一方向第 3 次不成功、或需要人操作时，立刻停下来报告。"**

## 六、并行与人机分工 → **详见 `03-parallel-and-budget.md`**

> **本节只留节奏相关的引子；三条线、子 agent 任务卡、人机分工、上下文纪律、token 账单的正文全部在 `03-parallel-and-budget.md`**（避免同一件事写两遍）。

- **接题即并行双线**（自己主线 + 子 agent 一条），不要等卡住才想起来派。三条线 = 主线 / 子 agent 线（fresh spawn，产物落盘绝对路径）/ 资源线（长任务后台 job + 逐进度日志，**断点可续**）。
- **派子 agent 前先过闸门**：顶层 ≤ 4、子会话 ≤ 8、任务卡只给路径不塞全文。细节见 `03-parallel-and-budget.md` §二 / §五。
- **人机分工的节奏含义**：需要人操作时**立即给一条可复制命令**，不要"我先把这条线跑完再说"——**用户每一次催促都是在说"你的循环太长了"**。

### 6.4 有效提示词模式（什么样的 prompt 真解出 flag）

| 模式 | 说明 |
|---|---|
| **新鲜重解** | "你根据题目重新解吧"——从附件原文重新推导。实测这一句连破两题 |
| **线索即提示词** | 题名/附件名/描述**逐字**写进分析（如 `How_many_rot_are_there` = 字母 ROT13 + 数字 ROT5；`flag^galf` = XOR 线索） |
| **定向子 agent 模板** | 已确认事实（勿重做）+ 已验证错误（勿重试）+ 疑点清单 + 最小验证步骤（模板全文见 `03-parallel-and-budget.md` §二） |
| **结构翻译** | 题面数学/代码结构先翻译成攻击原语再写码（`e=2^16`→`gcd(e,φ)=4`→`m^4` 开两次平方根；打印 `pow(AES_KEY_ENC,d,q*r)` = 泄露 PKCS1 明文块） |
| **最小样本验证** | oracle 先 `7*7==49` 单请求验证；WAF 先单字符 fuzz；成立再规模化 |
| **矛盾即信号** | 两次结果不一致、oracle 自相矛盾 → 停手查工具/链本身 |

## 七、上下文纪律与资源预算 → **详见 `03-parallel-and-budget.md` §四 / §五**

**本节只保留与"时间盒/收口时机"直接相关的一句话版**；实测账单（67 会话 / 10.6 亿 token / 90% cacheRead / 单步 528:1 / 开赛 14 分钟主控停摆 / 次日集体掐断）、12 条机械化防线、动态靶机配额线、时间线复盘**全部在 `03-parallel-and-budget.md`**。

**节奏视角下必须记住的三条**（展开见 03）：

1. **花费 ≈ 上下文体积 × 步数**——多开一个会话不是线性加钱，是每一项都乘一个 10 万～28 万的常数。**"再开一条线"是一个要花预算的决定，不是免费的。**
2. **停止信号 = 收口信号，不是"再试一次"信号**：响应延迟 >20 s / 连续 `TRANSPORT` 失败 / 子会话被运行时自动 stop → 立刻要回结论、写 handoff、**停止加派**（这条与 §五 停止条件 5 是同一个闸门）。
3. **每 30 分钟一次巡检**（tokenUsage + 响应延迟）要进计时器，和 15 分钟时间盒一起跑。

## 八、一页赛前检查单

```
[ ] **进题第一件事：加载对应平台 skill，读红线与授权范围**（禁扫描/爆破/重放，只做题目范围内交互）
[ ] **预算与并发上限写进 README**：token 总额 / 每会话上限 / 顶层 ≤4 / 子 ≤8
[ ] 先取题名/题面/`task.json`（有 `solved_count`、`attachment`、`hints`）/附件/flag 格式，再动手
[ ] 逐题通读题名/附件名/描述（**线索先于技术**）
[ ] 平台能登 / 录屏已开 / 手机开机（裁判会打）
[ ] 官方 WP 模板已下载到本地（记下路径，赛后会话要复用同一份）
[ ] 工作目录建好：chals/<题号>/ 一题一目录
[ ] flag 总账文件建好（flags.md）—— 唯一权威源，拿到 flag 立刻回填；**状态列只写平台回执**
[ ] 动态环境配额确认过（每账号可开几个场景）+ 登记表 + 释放人定好
[ ] 交接提示词模板备好（新会话直接粘）；子会话任务卡模板备好（**只给路径，不塞全文**）
[ ] 工具自检：python/tshark/objdump/gdb/IDA/浏览器/hashcat 真的能跑（固件类还要 binwalk/unsquashfs）
[ ] 计时器：15 分钟时间盒；**30 分钟 tokenUsage + 响应延迟巡检**也进计时器
[ ] 铁律默读：证据优先 / 静默失败先怪自己 / 到点换线 / **延迟飙升就收口**
```

**开局 10 分钟固定动作**：清点题目 → 按"15 分钟内能否解"分快题/硬题 → 先做快题 → 同时把硬题的信息（附件名/题名/描述）**逐字**读一遍（线索常常就在题面里）。

**开局 5 分钟精简版（短赛）**：preflight + 环境自检 + `--list` + 逐题通读题名/附件名/描述。

## 九、赛中两个定时动作（最容易漏，漏了直接丢分或丢 WP 素材）

- **每解出一题** → ①立刻回填 `flags.md` ②立刻写本题 WP 片段 ③立刻提交 flag ④截图存到该题目录。
- **交 WP 前** → 去排行榜搜队名，截**排行榜截图** + **答题情况截图**（官方模板硬要求"解题情况"栏；**赛后补不出来**——真事故就是漏了这张，导致连总题量都无法还原）。

**截图纪律**：多数赛事要求"关键步骤截图"。全程录屏时把重要一步顺手截一张存到题目录，别赛后补（补不出来）。不伪造截图（伪造属违规另行处理）。

**flag 本地自检三件套**（提交前）：格式 / 长度 / 字符集。**每题提交次数有限（常见 ≤50 次）：确信再交；拿不准先留证据。** 确认正确才停其他线；提交错误（假 flag）不停线。

## 十、赛后固定顺序

### 10.1 WP 窗口（常见赛后 2 小时）

1. 对齐"解出的题"清单 = `flags.md` 的条数（**少写任何一题 → 整份 WP 无效**）。
2. 逐题把 `.md` 片段拼成**一份**全队文档，**文件名含战队名**。
3. 逐题自检：flag 能在文中搜到；章节顺序与官方模板一致；自写脚本是**代码文本**不是截图。
4. **过期的片段必须先更新**（真事故：某题片段停在"flag 待补"，而 flag 早在 40 分钟前就拿到了——交付物内部矛盾会被评审直接怀疑真实性）。
5. 提交后留一份本地副本 + 截图存档。

**提交通道按场次不同，别套用上一场**：
- 有平台 `submit-writeup` 接口的 → 走接口（注意 `enablePlayerSubmitWriteup` 开关，见平台 skill）。
- 有**官方邮箱通道**的 → 汇总一个 pdf/md 发官方邮箱，**邮件主题 = 排名-团队名称**，按官方"附件模板"结构编写。
- **一个队伍只有一次 WP 提交机会的赛事** → **比赛中绝不提交任何 WP**（平台接口和邮箱都不交），每题 WP 只写进本地目录，赛后合并一次交。

### 10.2 复盘（把这场变成下一场的能力）

- 把新踩的坑按「**结论 + 证据 + 对策**」写进 playbook 错误模式清单；新的可复用技术写进亮点清单。
- 更新工具链状态记录（哪些工具真用上了、哪些是多余的）。
- 赛后取证的通用手法：**DSH 会话原始日志是本场唯一可信的"事实基线"**——`<HARNESS_HOME>\sessions\<workspace>\<sid>\session.v3.jsonl.zstd`，解压后逐事件统计即可拿到 ①每个会话的真实起止时间 ②每步 token 用量 ③**平台回执原文**。复盘"到底发生了什么"先跑这个，别靠回忆。

> **没写下来的教训等于没发生。**

## 附：跨场稳定的两条硬纪律（容易在长赛里丢）

- **每题解完立即记录**；卡 15 分钟换方向；**先解简单/高分题**。
- **批量工具一律后台 job，不阻塞主循环**。
- 不把 flag 写进无关位置；**提交后不留明文于临时文件之外**。
- 若平台行为与记录不一致，**以官方文档中心导出文档为准**，更新客户端并留注释。
- **平台/提交流程每次改动都要当场记入知识库**——真事故：曾成功提交过合并 WP，但当时方法未留存，次日重新摸索花了很多时间。**不要再丢。**
