## 一、flag 口径：先钉口径，再算答案

### 1.1 三条通用纪律（§5.1）

1. **本地自检**：格式 / 长度 / 字符集 → 再提交。
2. **诱饵 flag 很常见**：题面、配置、公告里的 flag 可能是烟雾弹，**以靶机真实可读的为准**。
3. **提交次数有限（常见 ≤50）**：**确信再交**；拿不准先留证据。
   补充：平台常同时限制提交**频率**（如 10 次/1 秒）⇒ **绝不写提交轮询脚本**，手工提交。

### 1.2 题面写法 → 口径对照表（★口径的全部权威来源，§7.1 ＋ §7.8）

| 题面写法 | 口径 | 证据 |
|---|---|---|
| `<hash前16位>_<hash后16位>` | `h = sha256(<答案的大写 hex 文本>).hexdigest()`；取 `h[0:16] + "_" + h[-16:]`，**小写输出** | 389 Pressure Gate，平台判正 |
| `GEELY{sha256_hex}`（裸 64 位） | `sha256(canonical.encode() + <恢复出的原始字节>)`，全 64 位**小写** | 390 官方提示原文（见 1.4） |
| `GEELY{TSP_<前24>_<后24>}` | `SHA256(SHA256(DER(SPKI)) ‖ SHA256(原始载荷字节) ‖ SHA256(新 header 字节) ‖ ASCII(tag))` → 取前 24 / 后 24 小写 hex | 395 TSP Shadow Rebinding，平台判正 |
| 帧预测题：`sha256(<下一帧的大写 hex 文本>)` | 同样取**大写 hex 文本**当哈希输入，前 16 ＋ 后 16、小写 | 389 家族（压力门 / CAN Noir 同模板） |
| 题面**额外**写「flag 大写」的题 | **才**用大写 | 391 / 392 |

**取口径的时机**：应在**拿到题面（分诊阶段）就先确认**，不是被判错后才回头对（真失误：铺了 9 条候选
被用户当场纠正"不要再猜了"）。
**拿不准口径时**：先找**同族标定样本**（同赛其它题的 protocol 文件、参考 flag）把约定钉死，再算**唯一解**。

### 1.3 已实测结论：**哈希输入取"文本形态"，不是原始字节**

| 算法输入 | 结果 | 判定 |
|---|---|---|
| `sha256("<答案的大写 hex 文本>")`（**大写 hex 文本**） | 前 16 / 后 16 = `<h[0:16]>_<h[-16:]>` | ✅ 平台判正 |
| `sha256(bytes.fromhex("<同一答案>"))`（原始字节） | 与上一行不一致 | ❌ 错 |

这条**直接解释了此前为什么 6 条候选必错**。定这个口径的方法是**用同赛已判正的题复算**：
389 已判正，就用它反推出 390 的口径。**同赛同模板的题，约定是共享资产。**
另（395）：所谓"新 header 字节"要用**紧凑 JSON 的原始字节**（与 trace 里所有 header 同格式），
**不是 base64 文本**。

### 1.4 裸 `sha256_hex` 题：**哈希输入不是 secret 本身**（§7.1.1，385 / 390 双题实测）

**已被平台拒绝的那些口径（别再试一遍）**：

| 试过的口径 | 结果 |
|---|---|
| 390：`sha256(secret 的大写 hex 文本)` | **平台已拒** |
| 385：`sha256(secret)` 原始字节 / 小写 hex / 大写 hex / `前16_后16` | **全部被拒** |
| 385：位序备选（左列=bit0、行倒读、列主序） | **全部被拒**（合计 **17+ 条**） |

**正解形状（390 官方提示原文）**：

```
flag = sha256(canonical.encode() + manifest_secret).hexdigest()
```

即 **先把一个 canonical 字符串与恢复出的原始字节拼起来，再 sha256**——不是对 secret 单独 hash。

**纪律**：

- 这种题**先确认题目里有没有定义 `canonical`**；**没定义就说明你还没找对材料**
  ——**不要靠枚举拼写 / 分隔符去撞**（385 上就是靠撞，白烧 **17+ 次提交**）。
- 材料里没定义的输入 → **第一时间向出题人 / 用户索要提示原文**；问一次远比猜 20 次便宜。
- 385 的同构写法（canonical = canonical tenant，即笔记里的"签名材料"）：候选清单位于工作区
  `zeekr-2026\chals\385-Ghost Fleet\复盘-385-Ghost-Fleet.md` §五——**接手该题时先读它，别从零重推**。
- 拿到"令牌 / 哈希 / 密钥"类中间量，**先本地跑一轮廉价猜测**（已知串拼接的 sha/md5/hmac、截断位置）
  再决定是否外包；**"不是朴素哈希"这个结论本身就是重要情报**（399：12 B 票据对 434 个朴素哈希候选全不匹配）。

### 1.5 提交纪律（§7.8 ＋ 候选纪律）

| # | 纪律 | 证据 / 说明 |
|---|---|---|
| 1 | **题面规则互斥时，找第三条证据把口径定死**——不要列"两种读法"当备选按顺序试 | `payload.version >= 250` 与 unlock 帧版本最高 243 互斥；grader 实际判正 **frame 188（v241）**：`>=250` 那条是对**当前状态帧**的规则，"original signed payload" = **唯一签名有效且 VIN 匹配**的真影子，两者**不冲突** |
| 2 | **提交前先查 `solved`**（多会话并行的队伍尤其要查），**验证通过立刻交**，绝不攒到最后 | §7.8 |
| 3 | **一题一答案**；写不出「判据 → 唯一解」就**不提交** | §7.8 |
| 4 | **候选闸门**：产出一条候选前先回答"我用什么判据认为它对？" | 真事故：铺出 60+ 条候选 flag、40+ 个脚本、7 MB 临时文件，把解题变成买彩票；用户两次纠正「不要再猜了，给我一个准确的答案」。完整错误模式见 `02-evidence-discipline.md` §三 |
| 5 | 答案形态**必须来自题目文本**（题面 spec / 公告 / 同族模板）：**先找公式定义处 → 再算 → 最后才提交** | 385 |
| 6 | **同一题最多给 2 条候选**；要给备选必须能指出"确实存在口径分歧"，且 **≤3 条并写明依据** | 385：连开 5 轮候选表（26→16→41→6→9 条），用户手工提交 17+ 条全错 |
| 7 | **接手同族新题，第一步读同族台账**（`flags.md`、`try_order*.txt`、已拒清单） | 385 的教训：先套了 389 的口径，而 390 台账里**早写着同一口径已被平台拒** |
| 8 | **被拒的候选要当约束用**：每被拒一条，写下一句"这否定了哪个假设"，据此**做减法** | 多条候选全被拒后仍横向乱试 = 假设空间没缩小（本例应立即推出"secret 或哈希输入之一必错"） |

## 二、flag 总账：单一权威源（§5.3）

### 2.1 三条硬规矩

1. 建一个 `flags.md`（或同名单文件）当**唯一** flag 总账；**拿到 flag 立刻回填**。
2. 任何 `WP-*.md` 片段里**不许出现"flag 待补"**——要么写 flag，要么不写那一段。
3. 交付前用一句话自检：**"`flags.md` 的条数 == WP 文档里的题数"**，不等就别交。

**真事故（为什么这三条是硬规矩）**：`WP-ghostpatch.md` 停在"flag 待补"，而 flag **早在 40 分钟前**就拿到了；
`flags.md` 停在 **14:19（只记 5 个）**，当天实际解出 **9 个**，剩下 4 个赛后**只能翻目录找**。
交付物内部矛盾会被评审直接怀疑真实性。

### 2.2 状态列只认平台回执（★★ 全库最重要的一条流程教训）

> 代价 = **白烧一整轮 ＋ 错误结论扩散三层**。

| 规则 | 内容 |
|---|---|
| **谁能写状态** | 「已判正」**只能由平台回执**写入：`code:1 "恭喜，提交的Flag正确!"` 或 task 查询 `solved=true` |
| **谁不能写状态** | 会话自述、脚本自检、"六条判据全过"**都不算状态**，最多写进备注列的 `[已验证]` |
| **回执要落盘** | **把回执原文＋时间戳抄进总账那一行**（既防自己忘，也是裁判抽查凭据） |
| **双向纪律 ①** | 「待提交」是**活待办**——截止前 20 分钟清点一次 |
| **双向纪律 ②** | **"我以为没交"也必须先验证再动手**（别凭印象重推或补交） |

**396 事故全过程（三层都记错的实例）**：

```
09:44:20  提交"干净值版"候选            → 平台拒绝
09:44:24  提交"LSQ 拟合值版"候选        → 平台判正（code:1）★ 真答案在这里
之后      总账 flags.md / 赛后复盘 / 运行时记忆  → 三层全写成「待提交」
次日      一整轮重解 → 推回了 09:44:20 那个【已被平台拒绝】的候选，并写进 WP
```

**⇒ 一条没人校验的台账 = 会自己繁殖的错误结论。**

配套：赛后清点时**列出当日唯一没有平台回执的题**，下一次开赛前先跟用户确认"它到底交了没有"
（本赛当日唯一无回执的是 397：其 flag 赛后复现两次一致，但从未确认提交）。
**未被回执确认的题 = 悬空状态，不是"已解出"。**

### 2.3 赛后复解任何一题之前：先用会话日志把状态钉死

```bash
# 先 grep 判正/判错回执，用回执钉死状态，再决定要不要重推
grep -a "提交的Flag正确\|提交的Flag错误\|solved=true" <解压后的会话事件流>
```

- 日志形态：DSH 的 `sessions/**/session.v3.jsonl.zstd`，**逐事件 JSONL**；
  提交事件形如 `[submit] task=N … ` 紧跟 `[resp] {code,msg}`。
- **会话原始日志是本场唯一可信的"事实基线"**：它同时给出 ①每个会话的真实起止时间
  ②每步 token 用量 ③**平台回执原文**。复盘"到底发生了什么"**先解压它统计，不要靠回忆**。
- 现成脚本（时间线 / 账单 / 单会话深摘 / **搜判正回执**）与用法、踩坑见 `30-local-toolchain.md`；
  账单与并发治理的用法见 `03-parallel-and-budget.md` §5.5。

## 三、AI 使用声明：每场规则不同，别套用上一场（§5.4）

| 赛制形态 | 规则 | 你要做什么 |
|---|---|---|
| **传统赛**（如长城杯） | 官方**鼓励**"合理运用 AI 工具、自研 AI 智能体辅助合作解题" | 如实声明即可，**不违规、不是扣分项** |
| **部分赛事把声明计入评分**（霄元杯：AI 审查占 **20 分**） | 必须**逐题**声明 | 逐题写清：**是否使用 / 使用环节 / 使用程度 / 独立思考说明** |
| **AI Agent 赛**（每队仅允许一个 Agent 接入平台） | 规则完全不同 | 选手**只能给方向性指导**，**不能给答案 / 解法提示**；解题必须由 Agent 完成 |

**通用动作**：开赛前**先把本场的 AI 规则原文抄进工作区 `notes/`**，赛中不再猜。
（三场赛事的规则差异与 WP 提交通道见 `20-competition-notes.md`。）
